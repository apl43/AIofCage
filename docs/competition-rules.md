# 比赛议题与项目交付规则

本文根据组织方提供的《2026 1024 Hackathon启动&规则介绍.pdf》和《Qiniu Builder Day-议题信息.pdf》整理，供团队开发对照。原文与团队执行约定分开记录；组织方后续通知优先。

## 一、所选议题原文

来源：《Qiniu Builder Day-议题信息.pdf》第 1 页，产品研发组。

> 桌面级安全沙箱：核心点是安全，其次是最终用户的友好性，不能是太技术化的配置。支持在沙箱内跑主流 agent 应用，如 claude code、codex、dsh 等，且所有主流 mcp 配置时均无需在沙箱内填写任何敏感信息（api key、password 等）。

解释：题目没有指定 Docker、Colima、Wails、hash 链或 AI 解说；这些是团队的技术选择。单个 Agent 和单个 MCP 跑通是阶段里程碑，不能直接等同于满足“主流”的完整范围；不支持的认证和平台需明确列出。

## 二、交付与开发规范原文

来源：《2026 1024 Hackathon启动&规则介绍.pdf》第 9 页，作品提交要求。

> 每个小组，可根据自己所属的赛组，自主选择1个议题，作品需符合所选议题方向的要求，自主完成作品。

> 2026年10月26日（周一）9:00 截止开发，代码仓库内将不允许再有任何修改痕迹。

> 请将产品所有源代码、如何运行程序的说明、架构设计文档（包含模块规格、分工）、录制的 demo 视频上传至 GitHub。

> 根据项目评估要求，您可自主选择云端或本地部署方式来准备演示环境。

> 请以更高工程规范要求自己，基于 pull request 提交每一次的变更！

> 代码仓库需要保留开发期间团队协同或个人创作的所有过程痕迹，只在最后一天一次性提交代码视为不合格。

> 如果是团队作品（而非单人作品），代码仓库需要有多人代码提交记录。

> 允许有 codebase，但不能只是拿现成的交差，我们会评估在 codebase 基础上团队新代码产生的贡献度进行价值判定。如果有 codebase，要求录入 codebase 后但还没有团队写的任何代码前，给代码打 v0 tag。如果有 codebase 但是没有打 v0 tag，作品将判定为无效，将取消比赛资格。

## 三、其他通用要求

| 项目 | 规则与来源 |
|---|---|
| 组队 | 1 至 3 人、一个议题、一份作品；见启动材料第 5 页；同赛道组队见第 7 页 |
| 工具资源 | AI 工具不限，通过内部网关提供每人 500 美元 token 资源；见第 11 页 |
| 研发赛道评分 | 商业价值与产品设计 50%，架构设计 20%，AI 价值呈现 15%，AI 工程效率 15%；见第 12 页 |

## 四、团队执行清单

- [ ] 按[产品目标与验收](requirements-and-acceptance.md)补齐范围、技术关口和证据；设计稳定并记录冻结后，再开始正式功能编码。这是团队流程，不是组织方新增条款。
- [ ] PR 合入 `shaoxier/AIofCage`，保留原始提交、作者和团队协作记录，不用 AI 生成的过程说明替代真实历史。
- [ ] 使用已有 codebase 时，按原文要求在团队新增代码前建立 `v0`；队友在本届比赛中新写的初始化代码属于团队开发成果，不倒改历史制造基线。
- [ ] 每个 Agent 和 MCP 明确记录支持、未验证、不支持，给出实际验证版本与复现方式。
- [ ] 同时核对 HTTP Token、OAuth、stdio、数据库密码的凭据代持与撤销；有限基线及未覆盖部分不能代替组织方对“主流”的范围认定。
- [ ] 运行说明覆盖专用 Colima 环境、启动、认证配置、排错、停止与清理，不包含真实密钥。
- [ ] 架构文档说明模块规格、实际成员分工、威胁模型、权限执行与审计边界。
- [ ] Demo 视频和源码上传 GitHub；使用可重建的测试项目与测试账号演示。
- [ ] 全部变更在 2026-10-26 09:00（上海时区）前完成；内部计划 07:00 前完成交付，留 2 小时缓冲。

统一仓库、内部缓冲时间、演示流程是团队约定，不额外包装为组织方的硬性条款。
