# PostgreSQL MCP 权限修复（2026-10-25）

## 已确认的问题

核对 `s9-db` 中 DeepSeek 原生会话的工具结果，而非只依据回复文字：`shopdb` 曾返回数据库容器的主机名、根目录列表，`COPY (SELECT ...) TO PROGRAM 'true'` 返回成功。实际数据库账号具备超级用户、建库、建角色、复制和绕过行级安全权限。

原连接器使用固定的 `@modelcontextprotocol/server-postgres@0.6.2`。检查实际安装的源码，发现其 `query` 工具只是先执行 `BEGIN TRANSACTION READ ONLY`，随后把任意 SQL 字符串交给驱动。只读事务不能限制数据库服务器的文件读取/程序执行能力，多语句也可改变事务状态。把工具命名为只读不能构成权限保证。

这些证据说明工具授权越界到数据库容器，不等于宿主机或内核逃逸。容器中的 `/etc/passwd` 不是宿主机文件；同一沙箱的会话共享 home/原生历史是现有产品边界。沙箱内可读的 `cage-*` 是该沙箱的内部占位凭据，不是上游密码；工具参数必须由服务端约束，不能依赖 Harness 自律。

## 改动

- 用自有 PostgreSQL 只读 MCP 服务替换参考服务，保留 `query` 和表结构资源接口。
- 用固定版本的 SQL 解析器校验结构，只接受单条 SELECT、只读 CTE、集合查询及允许的内置函数。拒绝文件函数、COPY、事务控制、嵌套写入、未知函数、危险类型转换和未知语法。
- 执行从语法树重新生成的 SQL，使用扩展查询协议、只读事务；限制语句长度、结构、时间、结果行数和返回体积。失败后完成回滚，状态不明的连接不复用。
- 每次读取前核验有效数据库权限，拒绝管理角色、危险预定义角色、可切换到管理角色的账号、可建库/建表或写业务表的账号。
- 依赖使用精确版本和 lockfile；镜像构建执行 SQL 策略回归。SQL、密码、连接串和驱动细节不返回给 Agent；界面说明改为必须使用专用只读账号。

## 实测

1. 四组 Node 策略测试通过，覆盖正常查表、聚合、联表、只读 CTE、字符串与日期；拒绝文件/程序调用、事务拆分、注释与大小写变体、嵌套写入、危险转换、过深结构及异常账号状态。
2. 真实专用 VM、一次性 PostgreSQL、门卫和连接器回归通过（最终 11.33 秒）。正常查询得到 `alpha,beta,gamma`，Claude CLI 连接和表结构资源可用；管理员与错误密码拒绝。
3. 直接在测试沙箱调用网关，七类越权请求全部返回工具错误。运行中新增表写权限、间接管理角色后，普通 SELECT 也被拒绝；撤销后恢复查询。三行原始测试数据未改变。
4. `s9-db` 的 `shopdb` 已切换为专用只读账号，密码进入新的钥匙串条目；原管理员条目保留，旧服务元数据备份在忽略的本地验证目录。只替换该 MCP 连接器，没有重启 Agent、门卫、数据库或 VM，项目与原生聊天历史保留。
5. 在原 `s9-db` 直接经网关回归：正常商品统计成功；读取主机文件、目录、执行程序和事务后写入全部拒绝。
6. 全部 internal Go 竞态测试、生产 vet/build、差异检查通过。新增依赖的 npm 审计报告为零已知漏洞（检查时点口径，不表示无未知风险）。

一次性数据库、沙箱与钥匙串测试条目已由测试清理。本轮未调用真实模型产生额外推理费用。

## 边界

数据库服务仍是明确授权的数据出口。只读账号应仅获得需要的数据表权限，数据库管理员不得向它授权不可信的安全定义者函数、视图或外部数据对象。SQL 允许范围有意收窄，不保证兼容所有 PostgreSQL 方言。该修复验证的是已列出的工具边界，不能宣称阻止全部容器逃逸。
