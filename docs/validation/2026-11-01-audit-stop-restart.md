# 正常停止不再报审计中断、重启不再记假缺口

[验收记录索引](README.md)

## 问题

11-01 决赛前全量实测的问题 F03：

- 每次在应用里正常停止沙箱，都会弹出红色提示“审计采集中断，正在从已保存的位置重试。日志和用量明细可能不完整。”
- 每次重启后，请求日志里多一条“日志有缺口（门卫已重启）”，用量页显示“存在 N 处日志缺口，统计可能不完整”。这次测试把演示沙箱 01—05 各重启了一次，它们现在各有一条这样的缺口。

两者都是误报：停止前的事件其实已经全部写进审计日志。

## 原因

1. **误报中断**：事件跟随连着门卫的事件流。停止沙箱时门卫关掉，事件流随之结束，但跟随要等下一次监视（最多 5 秒）发现门卫停了才取消。在这之前它把“流结束”当成异常，弹出中断提示。
2. **假缺口**：门卫每次启动是新的一轮，事件序号从 1 重新开始。应用重连时带着上一轮最后一条事件的位置，门卫认不出这个位置，就先发一条“游标来自另一轮”的缺口。这是 10-25 审计恢复时有意保留的设计：门卫不知道上一轮还有没有事件没被采到，宁可声明缺口，也不能悄悄跳过（见[审计恢复链路](2026-10-25-audit-recovery.md)）。问题在于应用从来没有告诉过门卫“上一轮已经采完了”。

## 改动

思路：缺口照样由门卫声明，应用只在自己确认过“上一轮已经全部落盘”时才不记录这一条。确认不了就照旧记录。

- **停止前收尾**（`internal/runtime/manager.go`、`internal/service/monitor.go`）：
  - 停止容器时的顺序本来就是 Agent、MCP 连接器、门卫。现在在停门卫之前加一步：问门卫这一轮最后一条事件的序号，等事件跟随把它写进审计日志（最多 3 秒），再把这个位置记在 `audit/<沙箱>.collected`。
  - 这时 Agent 和连接器已经停了，不会再有新的请求事件。
  - 应用里的停止、重置、添加或更新智能体都经过这一步。
  - 不收尾的情况：没有在跟随（比如应用刚打开还没订阅）、3 秒内没写完、Agent 没停下来、这一轮门卫一条事件都没有。这些情况不记位置。
- **重启时不记假缺口**：跟随重连时，如果带的位置正好是记下的“已采集完”的位置，门卫开头那条“游标来自另一轮”就不写进日志，接着照常记录新一轮的事件。其他缺口照常记录：没收尾的停止（比如在应用外停掉、虚拟机关机、门卫崩溃）、缓冲区溢出。
- **门卫停了不报中断**：事件流结束后照旧等 2 秒，然后先看门卫容器还在不在运行：
  - 已经停了：跟随直接结束，不提示。门卫再启动时由监视重新订阅。
  - 还在运行，但上一轮已经收尾：说明门卫马上又启动了新一轮（添加或更新智能体、重置后恢复运行），直接重连，不提示。
  - 其他情况：照旧提示“审计采集中断”并重试。Docker 查不到状态时按“还在运行”处理，真正的中断不会被吞掉。
- 跟随自己结束时，从订阅表里删掉自己（已经被换成新订阅的不动）。以前删掉的沙箱，它的跟随会一直每 2 秒重试，现在也会结束。

## 自动测试

- `internal/service`：
  - `TestAuditCollectedRunRestartsWithoutGap`：收尾后记下位置；应用重开后（游标和位置都从磁盘读）重连，“游标来自另一轮”不记录，用量里 0 处缺口。
  - `TestAuditUncollectedRunKeepsGap`：没在订阅时不收尾；跟随只写到第 4 条、门卫有第 5 条时，等到超时也不记位置，重启后照常记 1 处缺口。
  - `TestAuditFollowerEndsQuietlyWhenGateStops`：门卫已停，流结束后不重试、不提示；门卫还在运行，提示中断并重试。
  - `TestAuditCollectedRunReconnectsWithoutAlert`：收尾后门卫马上又启动，重连不提示中断，新一轮没有缺口。
  - 原有的 `TestAuditCrossRunGapDoesNotAcknowledgeLostEvents`、`TestAuditRetriesFromDurableCursorAfterWriteFailure` 不改，照样通过：没收尾时跨运行缺口照记，写盘失败照旧提示中断并从原位置重试。
- `internal/runtime`：`TestAppFinishesAuditBeforeGateStops`：收尾时 Agent 已经停了、门卫还没停；门卫没在运行或 Agent 没停下来时不收尾。
- 变异检查：分别去掉“跳过已采集完的缺口”“门卫停了就结束”“必须写到最后一条”三处判断，对应的测试都失败。
- `make check`、`make test`（含竞态检查）、前端 `node --test` 都通过。

## 真实环境验证

`AIOFCAGE_AUDIT_E2E=1 go test -run TestAuditRecoveryEndToEnd ./internal/service/`，专用 `colima-aiofcage` 环境，一次性空白沙箱（临时数据目录，不调用模型，不动已有沙箱和虚拟机），27 秒通过。这个测试原来断言“停止再启动后一定有跨运行缺口”，现在改成和桌面应用一样由监视循环订阅，覆盖三种停止：

| 步骤 | 结果 |
|---|---|
| 前半段不变：审计文件临时不可写，再恢复 | 提示采集中断；恢复后从原位置补齐 2 条被拒请求 |
| 正常停止，马上启动（像添加或更新智能体） | 停止前记下了采集完的位置；重启后第 4 条被拒请求照常记录；没有缺口，没有中断提示 |
| 正常停止，等 8 秒（跟随已经结束）再启动 | 监视重新订阅；第 5 条照常记录；没有缺口，没有中断提示 |
| 停门卫前不收尾（模拟在应用外停掉） | 重启后记 1 处“游标来自另一轮”缺口；第 6 条照常记录 |

测试结束后临时沙箱的容器、网络和项目文件夹都已删除，虚拟机里的 Docker 网络数回到测试前的 27 个。

## 范围与限制

- **已有的假缺口不会消失**：演示沙箱 01—05 在 11-01 测试里各留下的一条缺口，以及更早停止、重启留下的，都还在审计日志里，用量页仍会提示。审计日志只追加，这次没有改动已有记录。
- **只有应用自己停的才收尾**：用 `cagectl` 停止、虚拟机关机、门卫崩溃时，应用来不及收尾，重启后照旧记缺口。这些情况下确实可能漏掉最后几条事件。
- **应用没开着的时候**：应用关着时停掉的沙箱没有收尾，下次重启会记缺口。应用退出时不停沙箱，这种情况只出现在用 `cagectl` 停止时。
- 没有在打包好的桌面应用里点“停止”“启动”看提示，用的是同一套代码路径（`runtime.Manager.Stop`、`Start` 和监视循环）。
