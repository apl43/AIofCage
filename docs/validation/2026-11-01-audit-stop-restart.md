# 应用停止沙箱时不再误报审计采集中断

[验收记录索引](README.md)

## 问题

11-01 决赛前全量实测的问题 F03：

- 每次在应用里正常停止沙箱，都会弹出红色提示“审计采集中断，正在从已保存的位置重试。日志和用量明细可能不完整。”
- 每次重启后，请求日志里多一条“日志有缺口（门卫已重启）”，用量页显示“存在 N 处日志缺口，统计可能不完整”。

这次只修第一条。第二条保持原样，原因见“没有去掉跨运行缺口”。

## 原因

- 事件跟随连着门卫的事件流。停止沙箱时门卫关掉，事件流随之结束。但跟随要等下一次监视（最多 5 秒）发现门卫停了才取消，在这之前它把“流结束”当成异常，弹出中断提示。
- 删除沙箱时还有一个附带问题：监视只遍历还存在的沙箱，删掉的沙箱的跟随永远不会被取消，每 2 秒重试一次，一直到应用退出。

## 改动

- `internal/runtime/manager.go`：
  - 加两个通知：`BeforeGateStop` 在停止容器时、停门卫之前调用（这时 Agent 和连接器已经停过），`GateStarted` 在启动门卫容器之后调用。
  - 应用里的停止、重置、添加或更新智能体都经过这两处，启动失败时的清理也一样。
- `internal/service/monitor.go`：
  - 收到“要停门卫”时记下这个沙箱。事件流一结束就看有没有这个记号：有，就说明是应用自己停的，跟随直接结束，不提示。
  - 必须在流一结束就看：添加或更新智能体时，停掉旧门卫后马上启动新门卫，新门卫一启动记号就清掉了。
  - 有记号期间不再订阅这个沙箱，免得连上正在关的门卫，再报一次中断。
  - 记号在三种情况下清掉：门卫再启动时；监视看到门卫已经停下时；最长一分钟后。最后这种是为了防止在应用外（`cagectl`）启动的门卫一直没人跟随。
  - 没有记号的流结束，比如门卫崩溃、在应用外停掉、审计文件写不进，照旧提示“审计采集中断”并重试。
  - 删除沙箱前也记下这个沙箱：删除直接移除门卫容器，不经过停止。监视每一轮还会取消已经不存在的沙箱的跟随，`cagectl` 删的也算在内。
  - 跟随自己结束时，从订阅表里删掉自己的那一条；已经被换成新订阅的不动。

## 没有去掉跨运行缺口

第一版曾尝试在停门卫前等跟随写完这一轮的最后一条事件，记下这个位置，下次启动时不记门卫声明的那条缺口。独立复查指出这样会把真实缺口藏掉，最后没有采用：

- **记号不作废**：一轮正常停止后记下位置；下一轮如果一条都没采到，比如启动失败、启动后 5 秒内又停了、应用关着时用 `cagectl` 启停过，再下一轮启动时位置仍然对得上，整轮事件就无记录、也无缺口。
- **在途请求**：门卫在请求结束时才记事件。停止时如果模型回复还没回来，门卫可能在“确认采完”之后又补一条，甚至在门卫退出后才收到回复。这时请求已经带着密钥发出、计入了额度，审计里却没有它。原来的跨运行缺口至少会把这种情况标出来。

要做对，需要门卫配合：在 `/health` 里给出在途请求数，并提供“封存这一轮”的接口；还要把记号绑定到下一轮，任何没确认的情况都作废。这要改门卫，所有沙箱的门卫容器都得重建，冻结前不做。所以每次重启仍记 1 处“日志有缺口（门卫已重启）”，用量页照常提示。这是 10-25 [审计恢复](2026-10-25-audit-recovery.md)定下的保守做法：门卫不知道上一轮还有没有没采到的事件。

## 自动测试

- `internal/service`：
  - `TestAuditFollowerEndsQuietlyWhenAppStopsGate`：应用停门卫时流结束，不重试、不提示；没有记号时提示中断并重试。
  - `TestGateStopExpectationEnds`：门卫再启动时记号清掉，一分钟后过期。
  - 原有的 `TestAuditCrossRunGapDoesNotAcknowledgeLostEvents`、`TestAuditRetriesFromDurableCursorAfterWriteFailure` 等不改，照样通过：跨运行缺口照记，写盘失败照旧提示中断并从原位置重试。
- `internal/runtime`：`TestAppIsToldBeforeGateStops`：通知在 Agent 停过之后、门卫停之前；门卫没在运行就不通知；Agent 没停下来也照样通知，因为门卫照样要停。
- `make check`、`make test`（含竞态检查）通过。

## 真实环境验证

`AIOFCAGE_AUDIT_E2E=1 go test -run TestAuditRecoveryEndToEnd ./internal/service/`，专用 `colima-aiofcage` 环境，一次性空白沙箱：临时数据目录，不调用模型，不动已有沙箱和虚拟机。32 秒通过。

这个测试原来手动跟随，现在改成和桌面应用一样由监视循环订阅：

| 步骤 | 结果 |
|---|---|
| 前半段不变：审计文件临时不可写，再恢复 | 提示采集中断；恢复后从原位置补齐 2 条被拒请求 |
| 应用里停止，马上启动（像添加或更新智能体） | 没有中断提示；第 4 条被拒请求照常记录 |
| 应用里停止，等 8 秒再启动 | 没有中断提示；监视重新订阅，第 5 条照常记录 |
| 门卫不是应用停的（停止时不发通知，模拟在应用外停掉） | 提示采集中断；重启后第 6 条照常记录 |
| 用量统计 | 三次重启各 1 处跨运行缺口，共 3 处；模型请求 0 |

第一次跑时，“马上启动”这一步报了中断：新门卫启动时记号已经清掉，跟随等 2 秒后才看记号。改成流一结束就看之后通过。测试结束后，临时沙箱的容器、网络和项目文件夹都已删除，虚拟机里的 Docker 网络数回到测试前的 27 个。

## 范围与限制

- 每次重启仍记 1 处跨运行缺口，见上一节；演示沙箱以前留下的缺口也还在。
- 门卫停止后，应用会马上取消跟随。如果这时门卫恰好在停止后第一时间崩溃，不会再报中断。重启后照常记缺口。
- 没有在打包好的桌面应用里点“停止”“启动”看提示。端到端测试走的是同一套代码：`runtime.Manager.Stop`、`Start` 和监视循环。
